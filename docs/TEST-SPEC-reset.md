# Test specification — the reset removes `volumes/` from a container before it asks for a password

Covers `scripts/linux/lib/remove-volumes.sh` and the step of `cleanup.sh` that calls it, specified in
`docs/FEATURE-reset.md`. Written 2026-11-03 on #32, before the code, and run the same day after it;
each block's *What it found* records the run and its controls.

## 1. What is being tested, and at which level

The function decides, four times over, whether to run something destructive and as whom: `rm` as the
operator, `rm` as root inside a container with the project directory mounted, `rm` as root on the
host. Each decision has a side on which data goes and a side on which it stays, so this is decision
logic in `CLAUDE.md`'s sense and **full branch coverage is required**: the guard's two refusals — *not
an absolute path below /* and *not an existing directory* — and its acceptance, plain `rm` succeeding and failing, `docker` present and absent, each candidate image
present and absent, the container run exiting 0 and not, the directory gone and remaining after it,
`sudo` present and absent, and the directory gone and remaining after `sudo`. Every one of those has a
row below, and the branches none reaches are listed in §4 so the claim can be checked.

**Unit, without Docker, is the level for all of it but one.** The function is shell; what it does is
run three commands and read a directory. A fixture directory, a stub `docker` and a stub `sudo` first
on `PATH` show every branch, and `tests/run.sh` runs them in the default tier — a fallback that is only
tested when someone remembers `--system` is a fallback nobody has seen work. The stubs stand in for
*what the commands do*, not for whether a container can really remove a `101499`-owned tree; that is
the one thing a stub cannot show, and **CU-7** is the documented manual check that shows it, on real
rootless Docker, with today's measurement recorded.

**How plain `rm` is made to fail, under every uid.** *Rewritten 2026-11-03, review of #32.* Until
this note the rows that need a failing `rm` relied on a directory `volumes/locked` of mode `0500` —
`rm -rf volumes` by an ordinary user is refused on `locked/keep`, since unlinking needs write on the
directory — and skipped under uid 0, where no mode refuses anything; the scenario meant to report
that skip asserted a constant against itself and was counted as a pass. The project's reproducible run
is `bun test` as uid 0 in the dashboard image (`HANDOFF.md`, *A tool the test host does not have*), so the
decision logic this section demands full branch coverage of could be green there having never run:
7 passes, 11 skips, and one of the 7 saying nothing. Now the fixture's `bin/rm` is a stub in every
row. It appends its arguments to `rm.log` as the other two stubs do, and with `LU_STUB_RM=refuse` in
the environment it prints `rm: cannot remove '<dir>/volumes/locked/keep': Permission denied` on stderr,
exits 1 and touches nothing; without the knob it `exec`s the real `rm` found with `command -v rm` when
the fixture was built, so CU-1 and CU-5 (4) still remove their tree with the real binary. The eleven
rows under CU-2, CU-3 and CU-4 run with the knob set, under root and not, and each now also reads
`rm.log` — one call, `-rf <dir>/volumes`, ahead of any `docker` or `sudo` call — which the symlink
could not show: that the plain leg is tried first, on the right target, was inferred until now. The
locked tree stays, `0500` and all, and the premise scenario is what it is for: under an ordinary uid
it holds that the real `rm` is refused by such a tree with that message, the measured fact the stub's
refusal stands in for; under uid 0 it is **skipped**, with `test.skipIf`, so bun's tally shows `1 skip`
and the scenario's own name carries the reason — a skip, never a pass. Considered and not taken,
measured 2026-11-03 in the recipe's container: `chattr +i` needs `CAP_LINUX_IMMUTABLE`, which it has
not (`Operation not permitted`); a read-only bind mount needs `CAP_SYS_ADMIN`; dropping to `nobody`
with `setpriv` or `su` — both present in the image — would run the real `rm` against a tree that is
really another uid's, but the stubs that stand in for root would then be `nobody` as well and could
not remove the tree they are told to, and the rows would skip wherever the dropper is missing, which
is the same gap under another name. The stub is the one option that owes nothing to the uid.

**How the stubs stand in for root.** The stub `docker`, told to succeed, takes the source of the `-v`
it was handed, makes it writable and removes `<source>/volumes` itself. The stub `sudo`, told to
succeed, does the same to the path after `rm -rf`. That is not a simulation of Docker; it is what
makes the function's *reading of the result* observable: a leg that was handed the wrong path removes
the wrong thing, the fixture is still there, and the check the function runs afterwards has to notice.

**Why the directory is a fixture and not `volumes/` of this checkout.** The function is destructive
by design. Every case hands it a `mkdtemp` directory and nothing else, and the contract case reads
`cleanup.sh` as text rather than running it.
